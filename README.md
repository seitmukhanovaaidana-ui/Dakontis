# eclipse_schedule: разбор SCHEDULE-файла и QC истории для адаптации модели

Инструмент на Python для файлов вида `FINAL_SCH.INC`, которые Petrel
экспортирует в составе гидродинамической модели (Eclipse-формат). Такой
файл — это не просто расписание для симулятора, а сама историческая
база: дебиты нефти/воды/газа и закачка по скважинам, помесячно, за всю
историю разработки. Инструмент вытаскивает эти данные в pandas/CSV,
ищет в них артефакты экспорта и готовит blind-test разбивку — то, что
нужно **до** запуска самой адаптации (history matching) в симуляторе.

Симулятор (Eclipse/tNavigator/OPM Flow) сюда не входит и не запускается —
это только работа с текстом самого дата-файла.

## Установка

```
pip install -r requirements.txt
```

## Что делает

```
python run_schedule.py --input FINAL_SCH.INC --start-date 1973-06-01 --output-dir results_sch
```

В `results_sch/` появятся:

- `wells.csv` — список скважин: имя, группа, координаты i/j, дата ввода
  (взята из блока WELSPECS, к которому она относится);
- `completions.csv` — история перфораций (COMPDAT): интервалы k1-k2,
  статус, коэффициент связи, дата;
- `history.csv` — вся история в длинном формате: скважина, дата, тип
  (producer/injector), дебиты нефти/воды/газа или закачки;
- `field_rates.csv` — дебиты **по полю**, пересчитанные прямо из истории
  (без запуска модели) — для сверки с фактическим графиком типа
  "Field Liquid production rate", плюс VRR (voidage replacement ratio,
  закачка/отбор жидкости) со скользящим средним;
- `field_rates_plot.png` — график этих дебитов;
- `qc_suspect_rates.csv` — подозрительные значения дебитов (см. ниже).

`--start-date` — это дата START из основного `.DATA` файла (в консоли
Eclipse-запуска пишется как `START 1 JUN 1973 /`). Она нужна, чтобы
верно датировать самые первые скважины/дебиты, которые в файле идут
**до** первого блока `DATES` (они относятся к начальному состоянию).

## QC: поиск "заглушек" в истории

Реальные измеренные дебиты у разных скважин почти никогда не совпадают
до 5-6 значащих цифр. Если несколько скважин в один и тот же месяц
показывают идентичный дебит — это почти всегда не совпадение, а
default/заглушка, попавшая в экспорт вместо пропуска. Пример из
реальных данных: на нескольких скважинах в один месяц стоит одно и то
же значение `0.114943` вместо настоящего факта.

```python
from eclipse_schedule.parser import parse_schedule
from eclipse_schedule.qc import detect_placeholder_rates

data = parse_schedule("FINAL_SCH.INC", start_date="1973-06-01")
suspects = detect_placeholder_rates(data.history, min_wells=2)
```

`min_wells` — порог: сколько разных скважин должны показать один и тот
же ненулевой дебит в один месяц, чтобы это попало в отчёт (по умолчанию
2). На реальных данных `gas_rate` обычно даёт намного больше срабатываний,
чем `oil_rate`/`water_rate` — это ожидаемо, если газ на промысле не
измеряется по каждой скважине отдельно, а считается по общему GOR;
отдельно стоит смотреть срабатывания по `oil_rate`/`water_rate` (`qc.query("field != 'gas_rate'")`)
— они значат либо реальный технологический факт (несколько скважин
одного куста с одинаковым замером), либо ошибку экспорта, которую стоит
сверить с первичкой перед тем, как использовать эти месяцы как цель
адаптации.

## Blind-test: обрезка истории по дате

Стандартная проверка качества адаптации — калибровать модель только на
части истории, а оставшийся хвост использовать как "слепой" тест
(модель его не видела при подборе параметров), сравнивая прогноз с
реальным фактом за этот период:

```
python run_schedule.py --input FINAL_SCH.INC --start-date 1973-06-01 \
    --split-date 2015-01-01 --split-output FINAL_SCH_history.INC
```

Это создаст `FINAL_SCH_history.INC`, обрезанный сразу после последнего
блока `DATES` не позже `2015-01-01` (со всеми относящимися к нему
WELSPECS/COMPDAT/WCONHIST/WCONINJH) — его можно подставить вместо
`FINAL_SCH.INC` в `INCLUDE` основного `.DATA` файла для адаптации, а
период после 2015 использовать только для сравнения прогноза с фактом.

## Как это устроено внутри

Код в папке `eclipse_schedule/`:

- `parser.py` — общий разборщик блоков ключевых слов (без знания полной
  грамматики Eclipse: понимает только то, что нужно — WELSPECS, COMPDAT,
  DATES, WCONHIST, WCONINJH; остальные ключевые слова между ними просто
  пропускаются) и `parse_schedule()`, собирающий из них таблицы pandas;
- `qc.py` — поиск дебитов-заглушек (`detect_placeholder_rates`);
- `diagnostics.py` — пересчёт дебитов по полю и VRR прямо из истории
  (`field_rates`, `voidage_replacement_ratio`);
- `splitter.py` — обрезка файла по дате для blind-test (`truncate_schedule`);
- `report.py` — сохранение таблиц в CSV и графика.

Пример структуры входного файла (маленький, синтетический, без реальных
данных месторождения) — `examples/schedule_example.INC`; тесты —
`tests/test_eclipse_schedule.py`.

Проверка:

```
python -m pytest
```

## Дальше: полноценная адаптация (history matching)

Этот инструмент закрывает только подготовительный шаг (извлечение и QC
факта). Сама адаптация — это отдельный контур поверх реального
симулятора (Eclipse/tNavigator/OPM Flow): генерация мультипликаторов
PERMX/PERMY/PERMZ/PORO по регионам (EQLNUM/FIPNUM), запуск ансамбля
прогонов и подбор параметров (например, ES-MDA через
`iterative_ensemble_smoother` или фреймворк ERT). В `eclipse_schedule`
такой оптимизационный контур не реализован — модуль отвечает только за
данные факта, на которые эта адаптация будет ориентироваться.
