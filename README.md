# eclipse_schedule: разбор SCHEDULE-файла и QC истории для адаптации модели

Инструмент на Python для файлов вида `FINAL_SCH.INC`, которые Petrel
экспортирует в составе гидродинамической модели (Eclipse-формат). Такой
файл — это не просто расписание для симулятора, а сама историческая
база: дебиты нефти/воды/газа и закачка по скважинам, помесячно, за всю
историю разработки. Инструмент вытаскивает эти данные в pandas/CSV,
ищет в них артефакты экспорта и готовит blind-test разбивку — то, что
нужно **до** запуска самой адаптации (history matching) в симуляторе.

Симулятор (Eclipse/tNavigator/OPM Flow) сюда не входит и не запускается —
это только работа с текстом самого дата-файла.

## Установка

```
pip install -r requirements.txt
```

Для графического окна дополнительно нужен модуль `tkinter` — он ставится
вместе с Python с сайта python.org автоматически (галочка "tcl/tk and
IDLE" включена по умолчанию в установщике), отдельно устанавливать не
нужно.

## Графическое приложение (просто: загрузили файл — увидели график)

Если не хочется работать с командной строкой каждый раз — есть окно с
кнопками:

```
python run_gui.py
```

Откроется окно:

1. **"Загрузить SCHEDULE..."** — выбираете файл (например `FINAL_SCH.INC`);
   перед этим (или после, и заново нажать "Загрузить") укажите поле
   **"Дата START"** — дату START из основного `.DATA` файла (например
   `1973-06-01`), иначе у самых первых скважин/дебитов не будет даты.
2. Наверху появится сводка: число скважин, перфораций, дат, диапазон дат
   и число найденных QC-подозрений.
3. Вкладка **"Дебиты по полю"** — график Liquid/Oil/Injection rate,
   пересчитанный прямо из истории (для сверки с фактическим графиком).
   Поле "Окно скольз. среднего VRR" + кнопка "Обновить график"
   пересчитывают VRR без повторной загрузки файла. Кнопка "Сохранить
   график..." экспортирует PNG/PDF.
4. Вкладка **"QC (подозрительные дебиты)"** — таблица дебитов, которые
   совпадают у нескольких скважин в один месяц (см. раздел "QC" ниже).
   Порог "Мин. скважин" и фильтр "Показать поле" (`oil_rate`/`water_rate`/
   `gas_rate`) помогают отделить технологические совпадения от реальных
   артефактов экспорта.
5. Вкладка **"Скважины"** — таблица WELSPECS: имя, группа, i/j, дата ввода.
6. Вкладка **"История по скважине"** — выбираете скважину из списка и
   видите её собственный график Oil/Water/Injection rate по времени —
   удобно, чтобы проверить конкретную скважину, попавшую в QC-отчёт.
7. Панель **"Blind-test: обрезать историю по дате"** (над вкладками) —
   указываете дату и жмёте "Сохранить обрезанный файл..." — получаете
   `*_history.INC` для адаптации только на части истории (см. раздел
   "Blind-test" ниже).
8. **"Экспортировать результаты..."** — сохраняет все текущие таблицы
   (wells/completions/history/field_rates/qc) и график в выбранную папку,
   как и CLI-версия.

## Что делает (командная строка)

```
python run_schedule.py --input FINAL_SCH.INC --start-date 1973-06-01 --output-dir results_sch
```

В `results_sch/` появятся:

- `wells.csv` — список скважин: имя, группа, координаты i/j, дата ввода
  (взята из блока WELSPECS, к которому она относится);
- `completions.csv` — история перфораций (COMPDAT): интервалы k1-k2,
  статус, коэффициент связи, дата;
- `history.csv` — вся история в длинном формате: скважина, дата, тип
  (producer/injector), дебиты нефти/воды/газа или закачки;
- `field_rates.csv` — дебиты **по полю**, пересчитанные прямо из истории
  (без запуска модели) — для сверки с фактическим графиком типа
  "Field Liquid production rate", плюс VRR (voidage replacement ratio,
  закачка/отбор жидкости) со скользящим средним;
- `field_rates_plot.png` — график этих дебитов;
- `qc_suspect_rates.csv` — подозрительные значения дебитов (см. ниже).

`--start-date` — это дата START из основного `.DATA` файла (в консоли
Eclipse-запуска пишется как `START 1 JUN 1973 /`). Она нужна, чтобы
верно датировать самые первые скважины/дебиты, которые в файле идут
**до** первого блока `DATES` (они относятся к начальному состоянию).

## QC: поиск "заглушек" в истории

Реальные измеренные дебиты у разных скважин почти никогда не совпадают
до 5-6 значащих цифр. Если несколько скважин в один и тот же месяц
показывают идентичный дебит — это почти всегда не совпадение, а
default/заглушка, попавшая в экспорт вместо пропуска. Пример из
реальных данных: на нескольких скважинах в один месяц стоит одно и то
же значение `0.114943` вместо настоящего факта.

```python
from eclipse_schedule.parser import parse_schedule
from eclipse_schedule.qc import detect_placeholder_rates

data = parse_schedule("FINAL_SCH.INC", start_date="1973-06-01")
suspects = detect_placeholder_rates(data.history, min_wells=2)
```

`min_wells` — порог: сколько разных скважин должны показать один и тот
же ненулевой дебит в один месяц, чтобы это попало в отчёт (по умолчанию
2). На реальных данных `gas_rate` обычно даёт намного больше срабатываний,
чем `oil_rate`/`water_rate` — это ожидаемо, если газ на промысле не
измеряется по каждой скважине отдельно, а считается по общему GOR;
отдельно стоит смотреть срабатывания по `oil_rate`/`water_rate` (`qc.query("field != 'gas_rate'")`)
— они значат либо реальный технологический факт (несколько скважин
одного куста с одинаковым замером), либо ошибку экспорта, которую стоит
сверить с первичкой перед тем, как использовать эти месяцы как цель
адаптации.

## Blind-test: обрезка истории по дате

Стандартная проверка качества адаптации — калибровать модель только на
части истории, а оставшийся хвост использовать как "слепой" тест
(модель его не видела при подборе параметров), сравнивая прогноз с
реальным фактом за этот период:

```
python run_schedule.py --input FINAL_SCH.INC --start-date 1973-06-01 \
    --split-date 2015-01-01 --split-output FINAL_SCH_history.INC
```

Это создаст `FINAL_SCH_history.INC`, обрезанный сразу после последнего
блока `DATES` не позже `2015-01-01` (со всеми относящимися к нему
WELSPECS/COMPDAT/WCONHIST/WCONINJH) — его можно подставить вместо
`FINAL_SCH.INC` в `INCLUDE` основного `.DATA` файла для адаптации, а
период после 2015 использовать только для сравнения прогноза с фактом.

## Как это устроено внутри

Код в папке `eclipse_schedule/`:

- `parser.py` — общий разборщик блоков ключевых слов (без знания полной
  грамматики Eclipse: понимает только то, что нужно — WELSPECS, COMPDAT,
  DATES, WCONHIST, WCONINJH; остальные ключевые слова между ними просто
  пропускаются) и `parse_schedule()`, собирающий из них таблицы pandas;
- `qc.py` — поиск дебитов-заглушек (`detect_placeholder_rates`);
- `diagnostics.py` — пересчёт дебитов по полю и VRR прямо из истории
  (`field_rates`, `voidage_replacement_ratio`);
- `splitter.py` — обрезка файла по дате для blind-test (`truncate_schedule`);
- `report.py` — сохранение таблиц в CSV и графика;
- `gui.py` — графическое приложение (окно с вкладками, см. выше).

Пример структуры входного файла (маленький, синтетический, без реальных
данных месторождения) — `examples/schedule_example.INC`; тесты —
`tests/test_eclipse_schedule.py`.

Проверка:

```
python -m pytest
```

## Дальше: полноценная адаптация (history matching)

Этот инструмент (`eclipse_schedule`) закрывает только подготовительный
шаг — извлечение и QC факта. Сам контур ассистированной адаптации
(генерация мультипликаторов по регионам, ансамбль прогонов, ES-MDA)
реализован отдельно — в пакете `history_match`, см. ниже.

---

# history_match: ассистированная адаптация (ES-MDA) поверх реального симулятора

Контур, который использует факт из `eclipse_schedule` и генерирует
ансамбль кейсов с мультипликаторами PERMX/PERMY/PERMZ/PORO по регионам
(EQLNUM/FIPNUM/...), запускает их и обновляет параметры методом ES-MDA
(Ensemble Smoother with Multiple Data Assimilation, Emerick & Reynolds,
2013) — до сходимости расчёта с фактом.

**Важно: сам симулятор (Eclipse/tNavigator/OPM Flow) сюда не входит.**
Прогон каждого кейса и чтение результатов (UNSMRY → таблица дебитов,
например через `resdata`/`ecl2df`) нужно делать там, где стоит
лицензионный симулятор — обычно не там же, где этот Python-код. Поэтому
инструмент работает в два шага: `init` строит кейсы, вы прогоняете их
сами и сохраняете результат в CSV, `update` делает один шаг ES-MDA и
готовит следующий ансамбль кейсов.

## Как это работает физически (без запуска симулятора)

Сетка и свойства (`FINAL_GRID.INC`, `FINAL_PROP_PERMX.GRDECL`, ...)
могут весить сотни мегабайт — копировать их на каждую реализацию
ансамбля (десятки-сотни раз) не нужно. Вместо этого на каждую
реализацию генерируется:

1. Маленький файл мультипликаторов (`*_MULT.INC`) — использует
   стандартную (не самопальную) возможность ключевых слов Eclipse
   `EQUALS`/`ADD`/`MULTIPLY`/`COPY`: последние два необязательных
   параметра записи — номер региона и имя регион-массива — ограничивают
   бокс операции только ячейками этого региона. Бокс берётся равным
   всей сетке, поэтому реальные (возможно несвязные) границы региона
   вычислять не нужно:
   ```
   MULTIPLY
     'PERMX' 1.350000  1 123  1 188  1 582  1 'EQLNUM' /
     'PERMX' 0.620000  1 123  1 188  1 582  2 'EQLNUM' /
   /
   ```
2. Маленькая копия `.DATA` файла с одной вставленной строкой `INCLUDE`
   на этот файл мультипликаторов (в секцию `EDIT` — Petrel обычно
   оставляет её пустой специально для таких правок) — все "тяжёлые"
   INCLUDE (GRID/PROPS/...) остаются как в оригинале.

Кейсы по умолчанию создаются **в той же папке**, что и исходный `.DATA`
файл — так относительные пути INCLUDE в нём продолжают работать.

## Шаг 1: `init` — построить начальный ансамбль

```
python run_history_match.py init \
    --data FINAL.DATA --region-file FINAL_PROP_EQLNUM.GRDECL --region-keyword EQLNUM \
    --properties PERMX,PERMZ,PORO --n-realizations 50 \
    --low 0.3 --high 3.0 --seed 1 \
    --run-dir hm_run
```

- `--properties` — какие свойства адаптировать по регионам (через запятую).
- `--low`/`--high` — границы мультипликатора (0.3–3.0 значит "от -70% до +200% от базового значения"); сэмплирование log-равномерное, чтобы 0.5x и 2x были одинаково вероятны.
- `--run-dir` — папка для метаданных ансамбля (пространство параметров, векторы, список кейсов); сами `.DATA`-кейсы по умолчанию лежат рядом с `--data` (см. выше), не в `--run-dir` — если нужно иначе, укажите `--case-dir`.

Появится `hm_run/iteration_0/manifest.csv` со списком путей к кейсам.
**Прогоните ваш симулятор на каждом из них.**

## Шаг 1.5: `collect` — автоматически прочитать результаты (нужен `resdata`)

Если симулятор пишет обычный UNSMRY (Eclipse/tNavigator/OPM Flow), не
нужно руками собирать таблицы из результатов — после прогона всех
кейсов итерации:

```
pip install resdata
python run_history_match.py collect --run-dir hm_run --iteration 0
```

Это прочитает `<кейс>.UNSMRY`/`.SMSPEC` рядом с каждым `.DATA` (через
`resdata` — ту же библиотеку, на которой работает ERT) и разложит их по
`hm_run/iteration_0/predictions/case_NNN.csv` в формате
`eclipse_schedule.diagnostics.field_rates()` — колонки `FLPR`→`liquid_rate`,
`FOPR`→`oil_rate`, `FWPR`→`water_rate`, `FGPR`→`gas_rate`, `FWIR`→`injection_rate`
(полный список — `history_match.unsmry.DEFAULT_KEY_MAP`; свой набор
ключей — флагом `--keys FLPR,FOPR,FWIR`). Кейсы, которые не удалось
прочитать (например, симулятор ещё не досчитал), просто пропускаются со
своей ошибкой в консоли — остальные всё равно попадают в `predictions/`.

Если такой возможности нет (нет `resdata`, или у симулятора нестандартный
вывод) — соберите `predictions/case_NNN.csv` вручную, тем же форматом:
колонки `date` + те же, что в `field_rates()` (`liquid_rate`, `water_rate`, ...).

## Шаг 2: `update` — один шаг ES-MDA

```
python run_history_match.py update \
    --run-dir hm_run --iteration 0 --n-iterations 4 \
    --data FINAL.DATA --observed field_rates.csv \
    --predictions-dir hm_run/iteration_0/predictions
```

`field_rates.csv` — это факт, тот же формат, что `field_rates.csv` из
`eclipse_schedule` (`python run_schedule.py ...`) — можно передать его
как есть.

Команда:
1. Считает невязку по каждому кейсу (`ensemble_misfits`) и печатает топ-5 лучших.
2. Делает один шаг ES-MDA (параметры обновляются в сторону факта, разброс ансамбля постепенно сокращается).
3. Строит `hm_run/iteration_1/manifest.csv` — кейсы для следующей итерации.

Повторяйте `update` с `--iteration 1`, `2`, ... до `--n-iterations - 1`,
каждый раз прогоняя симулятор заново на новом `manifest.csv`. `alpha`
(коэффициент инфляции) на каждой итерации выбирается автоматически так,
чтобы сумма `1/alpha` по всем `n-iterations` была равна 1 (стандартная
схема ES-MDA с равными весами).

## Как это устроено внутри

Код в папке `history_match/`:

- `parameters.py` — `ParameterSpace`: фиксированный порядок параметров
  (регион, свойство), упаковка/распаковка в log-вектор, сэмплирование
  априорного ансамбля;
- `regions.py` — чтение уникальных номеров региона из GRDECL-файла без
  разворачивания всего массива (`parse_region_ids`), чтение DIMENS
  (`read_dims`), генерация MULTIPLY-файла (`generate_multiplier_include`);
- `ensemble.py` — сборка кейса (`build_case`/`build_ensemble`) и
  тонкая обёртка над `subprocess` для запуска реального симулятора
  (`run_case`) — она ничего не знает про Eclipse, просто подставляет
  путь к кейсу в вашу команду;
- `objective.py` — невязка между расчётом и фактом (`misfit`,
  `ensemble_misfits`) и упаковка факта/расчётов в векторы для ES-MDA
  (`observation_vector`, `predictions_matrix`);
- `es_mda.py` — сам алгоритм ES-MDA (`es_mda_update`,
  `run_history_matching_loop`) — реализован на чистом numpy, без
  внешних пакетов (ERT/`iterative_ensemble_smoother`), поэтому
  проверяется тестами на игрушечной аналитической модели без всякого
  симулятора;
- `unsmry.py` — чтение результатов реального прогона (`read_field_rates`,
  через опциональную зависимость `resdata`) в формат `field_rates`.

Тесты (`tests/test_history_match.py`, `tests/test_unsmry.py`) покрывают
все модули, включая чтение UNSMRY — `resdata` умеет не только читать,
но и писать summary-файлы, поэтому тест генерирует настоящий (не
поддельный) бинарный UNSMRY и прогоняет его через `read_field_rates()` —
единственное, что действительно нельзя проверить без Eclipse/tNavigator,
это сам запуск симулятора (`ensemble.run_case`) — там тестируется только
механика подстановки команды.

```
python -m pytest
```
